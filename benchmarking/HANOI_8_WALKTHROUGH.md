# hanoi_8 — the exact hierarchy the agent built, and how it used it

A full trace of one dynamic (n-level) run: every action it defined, how each
level relates to the one below, and the call sequence that solved the task.

**Run:** `results/gpt-5.5/dynamic-hierarchy/hanoi_8_20260807_144651/`
**Model:** gpt-5.5, reasoning effort `low`, 8,192 max output tokens/call
**Result:** solved, optimal — 255 moves, **0 replans**, 14 model calls, 5,923 output tokens

---

## 1. The base action (H1)

Generated by the unchanged H1 stage, before any planning:

```
MoveSingleRing(source_peg, target_peg)
    = [MoveCoroutine(source_peg), GrabCoroutine(), MoveCoroutine(target_peg), DropCoroutine()]
```

This is the only action that touches H0 primitives. Everything above is built
from it.

## 2. The hierarchy the agent invented

Six definitions, emitted in a single call, verbatim:

```
H2_MoveTower2(source_peg, target_peg, auxiliary_peg) = [
    MoveSingleRing(source_peg, auxiliary_peg),
    MoveSingleRing(source_peg, target_peg),
    MoveSingleRing(auxiliary_peg, target_peg)]

H3_MoveTower3(source_peg, target_peg, auxiliary_peg) = [
    H2_MoveTower2(source_peg, auxiliary_peg, target_peg),
    MoveSingleRing(source_peg, target_peg),
    H2_MoveTower2(auxiliary_peg, target_peg, source_peg)]

H4_MoveTower4(source_peg, target_peg, auxiliary_peg) = [
    H3_MoveTower3(source_peg, auxiliary_peg, target_peg),
    MoveSingleRing(source_peg, target_peg),
    H3_MoveTower3(auxiliary_peg, target_peg, source_peg)]

H5_MoveTower5(source_peg, target_peg, auxiliary_peg) = [
    H4_MoveTower4(source_peg, auxiliary_peg, target_peg),
    MoveSingleRing(source_peg, target_peg),
    H4_MoveTower4(auxiliary_peg, target_peg, source_peg)]

H6_MoveTower6(source_peg, target_peg, auxiliary_peg) = [
    H5_MoveTower5(source_peg, auxiliary_peg, target_peg),
    MoveSingleRing(source_peg, target_peg),
    H5_MoveTower5(auxiliary_peg, target_peg, source_peg)]

H7_MoveTower7(source_peg, target_peg, auxiliary_peg) = [
    H6_MoveTower6(source_peg, auxiliary_peg, target_peg),
    MoveSingleRing(source_peg, target_peg),
    H6_MoveTower6(auxiliary_peg, target_peg, source_peg)]
```

### How each level relates to the one below

Every level above H2 has **exactly the same shape**:

```
Hk(source, target, aux) = [ H(k-1)(source, aux, target),      # park the k-1 stack on the aux peg
                            MoveSingleRing(source, target),   # move the one ring now exposed
                            H(k-1)(aux, target, source) ]     # rebuild the k-1 stack on the target
```

Only two things change from one level to the next: which level it calls, and how
the three peg arguments are permuted. The agent wrote the recursive step of Tower
of Hanoi once and instantiated it six times, because the mapping notation has no
arithmetic and no base case — a function may not call itself, so genuine
recursion has to be unrolled into numbered levels.

H2 is the only one written directly in terms of `MoveSingleRing`, since a 2-ring
tower needs no sub-tower.

### Level assignment

The agent never labelled any of these. `dynamic_scoring.infer_levels` derived
the depths from the call graph, `level(primitive) = 0`,
`level(f) = 1 + max(level of callees)`:

| action | calls | inferred level | rings it moves | moves it expands to |
|---|---|---|---|---|
| `MoveSingleRing` | H0 primitives | 1 | 1 | 1 |
| `H2_MoveTower2` | MoveSingleRing | 2 | 2 | 3 |
| `H3_MoveTower3` | H2, MoveSingleRing | 3 | 3 | 7 |
| `H4_MoveTower4` | H3, MoveSingleRing | 4 | 4 | 15 |
| `H5_MoveTower5` | H4, MoveSingleRing | 5 | 5 | 31 |
| `H6_MoveTower6` | H5, MoveSingleRing | 6 | 6 | 63 |
| `H7_MoveTower7` | H6, MoveSingleRing | 7 | 7 | 127 |

The naming happens to match, but the levels are computed, not read off the names.
Note the invariant: **level = number of rings the action moves**, and the moves it
expands to are 2^level − 1. Each level adds exactly one ring, which is why depth
grows linearly with task size.

Reported depth is 7, not 8: the top action handles 7 rings, and the plan deals
with the 8th ring itself.

## 3. The plan (DecisionBot, natural language only)

Eight checkpoints, no function calls — the DecisionBot never sees a composed
action and is never given a call format:

1. `ring_1`…`ring_7` stacked on `peg_b` in size order, `ring_8` alone on `peg_a`
2. `ring_8` on `peg_c`, `ring_1`…`ring_7` still on `peg_b`
3. `ring_7` above `ring_8` on `peg_c`, `ring_1`…`ring_6` on `peg_a`
4. `ring_6` above `ring_7` on `peg_c`, `ring_1`…`ring_5` on `peg_b`
5. `ring_5` above `ring_6` on `peg_c`, `ring_1`…`ring_4` on `peg_a`
6. `ring_4` above `ring_5` on `peg_c`, `ring_1`…`ring_3` on `peg_b`
7. `ring_3` above `ring_4` on `peg_c`, `ring_1`,`ring_2` on `peg_a`
8. all eight rings on `peg_c` in size order

## 5. What is worth noticing

**The structure is a descending staircase, not one big call.** Subtask 1 parks
seven rings, subtask 2 moves the largest ring, then subtasks 3–8 rebuild the
tower one ring at a time using a progressively smaller macro: H6, H5, H4, H3, H2,
then bare moves.

Subtasks 3–8 total exactly 127 moves — precisely what a single
`H7_MoveTower7(peg_b, peg_c, peg_a)` would have produced. So the agent could have
solved this in **3 top-level calls instead of 15**, with identical moves and
identical optimality. It chose to unroll the rebuild into six checkpoints because
the *plan* asked for six checkpoints.

That matters for cost, not correctness: each subtask costs one OuterBot
verification call. hanoi_8 used 14 model calls where hanoi_12 — with a coarser
3-subtask plan — used 9. **Plan granularity, not hierarchy depth, is what drives
the call count.** This is also why per-task token numbers are noisy between runs.

**The emission is what makes it work.** The six definitions are 1,206 characters.
Enumerating the same 255 moves flat, as the two-level pipeline must, takes ~7,648
characters — 6.3× more, and that gap doubles with every additional ring.

For comparison, the two-level pipeline on the same task:

| | 2-level | n-level |
|---|---|---|
| hierarchy output | 8,799 chars | 2,472 chars |
| output tokens | 28,481 | **5,923** |
| replans | 3 | **0** |
| result | solved, optimal | solved, optimal |

Both solve hanoi_8. The two-level pipeline needed three correction rounds and
4.8× the tokens to get there — and two rings later, at hanoi_10, it needs ten
rounds, and at hanoi_11 it stops working entirely.
